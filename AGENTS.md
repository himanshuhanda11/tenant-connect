# Project rules

- Workspace-scoped Meta (Facebook) data syncs (lead forms, pages, leads) must use only that workspace's own connected token from `smeksh_meta_ad_accounts`; never fall back to the platform `META_SYSTEM_USER_TOKEN`. Why: the platform token belongs to another business and leaks its Pages/forms into unconnected workspaces.
- Facebook tokens are server-only: browsers never receive, send or store them. Connect/reconnect/refresh/save go through the `meta-ads-fb-login` edge function (pending tokens in `meta_oauth_pending`), and the browser selects `smeksh_meta_ad_accounts` only via `META_AD_ACCOUNT_PUBLIC_COLUMNS` (column privileges block `meta_access_token` and `select('*')`). Why: any workspace member could previously read the token, and a browser-written Page ID could route another business's leads.
- Meta connection problems are classified by `supabase/functions/_shared/metaAdsDiagnosis.ts` (unit-tested in `src/test/meta-ads-diagnosis.test.ts`); add new causes there instead of ad-hoc UI messages. Why: one source of truth for customer-facing recovery steps.
- A workspace keeps one active WhatsApp number. Replacing or disconnecting a number goes through `supabase/functions/_shared/whatsappNumberRelease.ts` (deregister in Meta, unsubscribe the WABA only when no active number still uses it, keep the row as `disconnected`, move chats/flows to the new number); never delete `phone_numbers` rows. Why: deletes cascade away campaign history, and label-only disconnects left numbers registered in Meta. Unit-tested in `src/test/whatsapp-number-release.test.ts`.
- Ad-based lead routing for Click-to-WhatsApp chats targets the WhatsApp `referral.source_id` stored in `meta_ctwa_ads` (filled by the webhook via `record_ctwa_ad_click`) and saved on automations as `trigger_conditions.meta_ad_ids`; matching and rule order (specific ads > campaigns > every ad, then oldest; first match assigns) live in `supabase/functions/_shared/metaAdTargeting.ts`, re-exported to the UI via `src/lib/metaAdTargeting.ts` so the routing page shows the same winner (tested in `src/test/meta-ad-targeting.test.ts` and `meta-ad-routing-priority.test.ts`), and ad automations run before general auto-routing. Why: workspaces without Meta ad-account access still need per-ad distribution, and ad-specific assignment must win over the workspace round robin.
- `whatsapp-webhook` verifies Meta signatures with `META_APP_SECRET` and, if that fails, `META_APP_SECRET_LEGACY` (the earlier Aireatro Meta app still delivers some WhatsApp accounts' webhooks to the same URL); helper in `supabase/functions/_shared/metaSignature.ts`, tested in `src/test/meta-signature.test.ts`. Why: rejecting the legacy app's signed deliveries silently dropped status updates for those accounts.
- Direct Chat greetings resolve as: the person's own active greetings, then workspace greetings written by owners/admins (via the `get_workspace_greeting_templates` RPC, since agents cannot read other members' roles), then built-in defaults. Why: agents previously never saw the greetings the owner set up.
- `meta-ads-sync` reads ads and insights with paged account-level calls (never one call per campaign) and keeps the previously saved ads/insights when Meta refuses a call. Why: per-campaign calls hit Meta's user request limit and blanked the live/paused status used by Ad lead routing.
- Per-ad "where leads went" counts come from the `get_ad_agent_lead_breakdown` RPC (contacts.campaign_source × latest conversation's assignee); "live" ads use Facebook status when synced, else recent chats (`isAdLive` in `src/lib/metaAdRouting.ts`, tested in `src/test/meta-ad-lead-breakdown.test.ts`). Why: one definition shared by the page and its tests.
- Agent performance metrics are defined once in the SQL function `_agent_perf_rows` (one row per agent × conversation × metric); `agent_performance_report` and `agent_performance_conversations` (drill-down) both read it, and "handled" means the agent sent a message (`messages.sent_by`, set by the send-* edge functions; older rows backfilled from assignment history with `sent_by_inferred`). Why: cards, table and drill-down lists must always agree and survive reassignment.
- Report date ranges are computed with `src/lib/workspaceTime.ts` in the workspace timezone (tested in `src/test/workspace-time.test.ts`) and sent to the database as exact UTC instants; never use the device timezone for reporting. Why: UAE/India workspaces need correct Today/Yesterday boundaries.
- Workspace timezone lives on `tenants.timezone` with `timezone_source` ('auto' follows the connected WhatsApp number via the `trg_phone_numbers_workspace_timezone` trigger and `suggest_timezone_for_number`; 'manual' = admin override and is never changed automatically). UI reads it through `useWorkspaceTimezone`; agent names in the inbox/reports come from `agents.display_name` via `useAgentDisplayNames`. Why: one reporting timezone and one agent label everywhere.
- Inbox "replied" (green) state is `isChatReplied` in `src/lib/inboxReplyState.ts` (agent's last non-auto reply ≥ customer's last message; tested in `src/test/inbox-reply-state.test.ts`); the inbox "My work" strip reads `agent_performance_report` so its numbers match Team › Agent performance. Why: one definition of replied/waiting across inbox and reports.
